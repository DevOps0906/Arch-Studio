## 2. 구조: 공유 코드와 셸 2개

원칙: 판정·도면·AI 호출 로직은 `packages/*` 한 벌, 셸은 "환경 접점"만 다르다. 화면은 Tauri API·Supabase를 직접 import하지 않는다(기존 규칙 `02_ARCHITECTURE.md` 2장 shell-bridge 행).

| 층 | 위치 | 내용 | 변경 |
|---|---|---|---|
| 공유 엔진 | `packages/{domain,geometry,rules,program,massing,layout,drafting,io}` | 순수 TS, UI·OS 비의존 | 없음(웹 워커에서 그대로 실행, 10장 4장 전제) |
| 공유 UI·기능 | `packages/ui`, `packages/features` | 화면 기능 단위, 주입받은 어댑터로만 데이터 접근 | 어댑터 주입 지점 추가 |
| 어댑터 | `packages/shell-bridge` | 플랫폼 인터페이스(아래) + 구현 2벌(`tauri/`, `web/`) | `web/` 구현 신설(기존 "웹 대체" 확장) |
| 셸 A | `apps/desktop`(Vite + Tauri 2.x, 기존) | 라우팅, 워커 생성, Rust 코어(fs·SQLite·키체인·license·updater) | 어댑터 `tauri/` 연결 |
| 셸 B | `apps/web`의 앱 라우트 신설 `src/app/(studio)/**`(제안) | 로그인 후 스튜디오. 라우팅·워커 생성·CSP는 셸 B가 소유 | 신설. 기존 `(marketing)`·`(account)`와 라우트 그룹 분리. **출처는 별도 서브도메인(예 `app.`)을 기본값으로**(5장 출처 분리) |
| 서버 | `apps/web/src/server/**`, `apps/api`, `workers/arch-jobs`, `supabase/` | 라이선스·AI·잡·클라우드 프로젝트 | `cloud-projects`·`licenses` 확장(7장) |

경계 규칙(제안):
- `packages/features`는 `apps/*`를 import하지 않는다. `(studio)`와 `apps/desktop`은 같은 `features` 라우트 정의를 공유하고 셸만 감싼다.
- `apps/desktop`의 `routes/**`와 `(studio)`의 페이지를 이중 관리하지 않도록, 화면 컴포넌트는 `features`에 두고 두 셸은 얇은 래퍼만 갖는다. 정적 번들(Vite)과 Next.js(App Router) 라우터 차이는 래퍼에서 흡수한다. 실현 가능성은 **W0의 1주 스파이크**(AR-06-071a)로 확인(미확인). 실패 시 대안: Vite SPA 하나에 `web` 어댑터를 붙여 정적 호스팅(Next는 마케팅·계정만).
- 엔진 워커는 두 셸 모두 `EngineRequest/Response` 프로토콜(`02_ARCHITECTURE.md` 2.4절)을 쓴다. 워커 파일 위치만 셸별.

### 2.1 플랫폼 어댑터 인터페이스 (계약 예시, 제안)

| 어댑터 | 책임 | 설치형 구현 | 웹 구현 |
|---|---|---|---|
| `ProjectStore` | 프로젝트·리비전 읽기/쓰기/목록 (저장 모드는 3장) | Rust `local_db_*`(SQLite) + 클라우드 모드 시 `CloudProjectClient` | `CloudProjectClient`(Supabase, RLS) + IndexedDB는 **읽기 캐시만**(3.1절) |
| `FileGateway` | 가져오기/내보내기 파일 I/O | OS 대화상자 경로(`fs.rs`, 크기 상한) | `<input type=file>`·File System Access API(가능 시)·다운로드 Blob. 크기 상한 동일 |
| `SecureStore` | 토큰·라이선스 파일 보관 | OS 키체인(`secrets.rs`) | 메모리 + httpOnly 쿠키 세션(쿠키 사용 시 CSRF 토큰 필수, 5장). 장기 비밀 보관 없음. 라이선스 파일 없음(서버 판정) |
| `EntitlementClient` | 권한 판정 | Rust `license.rs`가 서명 파일 검증(로컬 기능) + 서버(클라우드 기능) | 서버 `arch.org_features`가 정본, 세션마다 조회 |
| `Updater` | 앱 업데이트 | Tauri updater(서명) | 없음(배포 즉시 반영). 규칙 팩은 서버 자격 판정 |

```ts
// packages/shell-bridge (계약 예시, 구현 파일 아님)
interface PlatformAdapters {
  projects: ProjectStore       // list/get/save(expectedRevision)/delete
  files: FileGateway           // pickOpen/saveAs, 크기 상한은 어댑터가 강제
  secrets: SecureStore
  entitlement: EntitlementClient  // can(feature): Allow | Deny(reason) , 만료/유예 상태 포함
  capabilities: { offline: boolean; localFiles: boolean; autoUpdate: boolean }
}
```
기능 코드는 `capabilities`로 UI를 분기하고 `platform === 'web'` 같은 직접 검사를 쓰지 않는다(제안).

## 3. 프로젝트 저장·동기화 정책 (MVP 범위 제안)

| 모드 | 정본 위치 | 대상 | MVP |
|---|---|---|---|
| 클라우드 | `arch.cloud_projects`(프로젝트 전체를 버전 붙은 단일 blob, 서버 `cloud-projects`). 관계형 복제(`model_revisions` 등)는 Phase 2 | 웹 기본. 설치형도 선택 가능 | 포함 |
| 로컬 전용 | SQLite(설치형 B 분류, `02_ARCHITECTURE.md` 2.2절) | 설치형, 오프라인 | 포함 |
| 수동 이동 | 로컬 ↔ 클라우드 "업로드/내려받기" 명령 | 설치형 사용자 | 포함(제안) |
| 자동 양방향 동기화 | 양쪽 | 설치형 | **Phase 2**. 기존 "동기화(C)는 MVP에 없다"(`02_ARCHITECTURE.md` 2.2절)와 일치 |

충돌 처리(제안): 병합하지 않는다. 클라우드 저장 시 `expected_version`(`04_API.md`의 동시성 토큰 이름으로 통일, 이 문서의 이전 표기 `expectedRevision` 폐기)을 보내 서버가 비교하고, 불일치면 거절 후 "내 변경을 사본으로 저장" / "서버 최신 열기" 두 선택만 준다(화면·오류 문구의 명칭은 이 두 개로 통일, `03_SCREENS_UX.md` 5.2 `AR041`; "두 버전 비교" 화면은 없다). 같은 프로젝트의 동시 편집은 막지 않되 위 규칙으로 데이터 손실을 막는다. 실시간 공동 편집은 범위 밖.

키 설계(제안, `05_DATA_MODEL.md` 로컬 B 분류·`cloud_projects` 변경 필요): 웹에서 새로 만든 프로젝트는 로컬 id가 없으므로 `project_uuid`를 정본 키로 하고 `local_id`는 nullable(설치형 업로드 시에만 채움). 업서트 계약: `(org_id, project_uuid)` 기준, `expected_version` 일치 시 `version+1`로 blob 교체.

| 항목 | 제안 |
|---|---|
| 로컬 ↔ 클라우드 복사 시 | 업서트 계약과 일치: **업로드 최초 1회는 새 `project_uuid` 발급(사본)**, 이후 같은 `local_id`로 올리면 같은 행에 업서트(`expected_version` 필요). 원본은 유지. 자동 양방향 동기화는 아님 |
| 클라우드 보존 | 구독·기간제 활성 + 영구(업데이트 유효) 동안 유지. 만료 시 열람·내보내기·내려받기 유지(기존 4.3절 원칙). 만료 후 보존·삭제·통지는 3.3절 제안(Q5, 사용자 승인 필요) |
| 클라우드 용량 | 상품별 한도(Q4). 원가 근거 `미확인`(Supabase Storage 단가 확인 필요) |
| 개인정보 | 클라우드에 올리는 데이터는 사용자가 저장 모드를 클라우드로 고른 프로젝트만. 대지 주소 등 분류는 `09_SECURITY_PLAN.md` 2장 |

### 3.2 저장 모드별 표시와 실패·충돌·단절·만료 (R4, 승인 2026-10-28)

웹은 클라우드 모드만 있다(로컬 모드 없음, 파일은 내보내기/내려받기). 헤더 저장 상태 줄과 프로젝트 목록(칩·버전·마지막 저장)은 모드를 항상 보인다. 문구 정본은 `03_SCREENS_UX.md` 5.1.

| 모드 | 헤더 표시 | 오프라인 문구 |
|---|---|---|
| 클라우드 | "클라우드 · v<n> · 저장됨 / 저장 중 / 저장 실패" | 설치형 "읽기 전용입니다. [로컬로 복사해 편집]은 사본이며 서버와 동기화되지 않습니다". 웹 "연결이 끊겨 읽기 전용입니다" |
| 로컬 전용 | "이 PC에만 저장됨 · 서버에 없음" | "이 PC의 프로젝트는 그대로 편집·내보내기됩니다" |
| 수동 사본 | "이 PC 사본 · 클라우드 v<n>에서 올림 · 동기화 안 됨" | 로컬 전용과 같고 "클라우드와 자동으로 맞춰지지 않습니다" 병기 |

| 시나리오 | 감지 | 화면 동작 | 작업 회수 동선 |
|---|---|---|---|
| 저장 실패(5xx·타임아웃) | 저장 응답 실패 | "저장 실패 · 다시 저장". 편집은 계속, 창 닫기·종료 시 미저장 경고 | [다시 저장] · [파일로 내려받기(.arch)] |
| 저장 거절(413·`AR040` 한도) | `AR031`·`AR040` | 원인 문구 + 저장 안 됨 표시 | 파일로 내려받기, 오래된 사본 삭제 |
| 충돌 | 409 `AR041` | 두 선택만: **내 변경을 사본으로 저장** / **서버 최신 열기** | 사본: 새 `project_uuid`·이름 "<이름> (내 변경)". 서버 최신 선택 시 "저장 안 된 변경 N건이 사라집니다" 확인 + [파일로 내려받기] 먼저 제공 |
| 통신 단절 | 요청 실패·오프라인 이벤트 | 클라우드 모드는 읽기 전용 전환(화면의 미저장 변경은 유지). 로컬·수동 사본은 변화 없음, 클라우드 버튼만 비활성 | 미저장 변경은 [파일로 내려받기]. 재연결 때 자동 저장하지 않고 사용자가 [다시 저장](충돌 검사 거침) |
| 만료·폴백·좌석 회수 중 저장 | 402 `entitled=false`(사유 `expired`·`fallback`·`seat_unassigned`·`seat_revoked`·`no_product`, `04_API.md` 1장) | "편집 권한이 없어 저장하지 못했습니다(<사유>)". 열람·내려받기는 유지 | [프로젝트 내려받기] · [전체 내려받기(zip)] · [Excel/CSV 내보내기(AR-F-044)] · [갱신·좌석 문의] |
| 만료 후 열람 | `rights.web_edit=false` | 읽기 전용 배너 + 보존 기한(유효 상품 0개 조직만). 영구 폴백(`fallback`) 조직은 보존 기한 없이 "업데이트를 갱신하면 바로 편집할 수 있습니다" | 내려받기 `GET .../blob`(402 예외), 설치형은 [로컬로 내려받기] |
| 보존 기한 도래 | 삭제 예약(유효 상품 0개 조직만, 폴백 조직은 해당 없음) | 삭제 7일 전부터 배너 | 3.3절 통지 |

### 3.3 만료 후 보존·삭제·데이터 회수 (승인 2026-10-28, Q5·D-H5 ①)

시계는 조직 단위: **조직에 유효 상품(영구 보유 포함)이 0개가 된 시각**부터 센다(확정 D-H5 ①). 좌석 배정 수가 아님: 좌석을 회수·미배정해도 유효 상품이 있으면 시계는 시작하지 않는다. 영구 라이선스를 가진 조직은 업데이트가 만료돼(`fallback`) `web_edit` 상품이 0개여도 시계를 시작하지 않는다. 시작 시각은 `cloud_retention_started_at`으로 영속 저장하고(`05_DATA_MODEL.md` 2.9절) 유효 상품이 다시 생기면 null로 리셋한다. 프로젝트는 조직 소유라 좌석이 미배정·회수된 멤버도 열람·내려받을 수 있다. 약관·개인정보 검토는 `미확인`.

| 항목 | 값(승인 2026-10-28) |
|---|---|
| 만료 후 보존 | 90일(읽기·내려받기·내보내기 유지, 편집·신규 저장 불가). 보존 중 유효 상품이 생기면 즉시 편집 복귀·삭제 예약 취소 |
| 사전 통지 | 만료 즉시 1회, 삭제 30일 전·7일 전(이메일 + 앱 배너). 발송 기록 저장소는 코어 알림 모듈 사용 여부 `미확인` |
| 데이터 회수 | 보존 기간 포함 언제든: 프로젝트별 .arch 내려받기 + Excel/CSV 내보내기 + **전체 프로젝트 일괄(zip) 내려받기(MVP 포함)**. 미배정·회수 사용자도 허용 |
| 삭제 | 보존 종료 후 blob·행 영구 삭제, 감사 기록. 백업 잔존 기간 `미확인` |

| 회수 vs 삭제 의무 | 계정 삭제·개인정보 파기 요청·조직 삭제는 보존 기간보다 우선한다. 사전 내려받기 안내(.arch·Excel/CSV) 후 즉시 삭제. 통지 문구 자리: "백업에서 최대 N일 후 완전 삭제됩니다"(N = 백업 잔존 기간 `미확인`, 근거 확인 필요) |

## 4. 라이선스 모델

### 4.1 상품 × 플랫폼 매트릭스 (구성안, 제안. 가격 확정 아님)

기존 상품(`01_PRD.md` 4.1·4.2절)은 영구(`perpetual_*`) + 업데이트(`updates_yearly`) + 월 구독(`sub_monthly`)이다. 기간제를 추가하고 구독에 연 결제를 더한다.

| 상품 | 결제 | 설치형 | 웹 | 업데이트·규칙 팩 | 만료 후 |
|---|---|---|---|---|---|
| 영구 `perpetual` | 일시불 | 영구 사용(PC 2대, 오프라인은 30일마다 온라인 재확인·열람/내보내기는 제한 없음, D-H5 ②가 D-7(a) 대체) | **업데이트 유효 기간(첫 1년 + `updates_yearly`)에 포함**. 만료 후 웹은 열람·내보내기만 | 첫 1년 포함, 이후 `updates_yearly` | 설치형 폴백 유지(`01_PRD.md` 4.3절). 웹 편집은 불가 |
| 기간제 `term` | 1년·3년 선결제(자동결제 없음) | 기간 중 | 기간 중 | 기간 중 전부 포함 | 열람·내보내기만(구독 만료와 동일) |
| 구독 `sub` | 월·연 자동결제 | 구독 중 | 구독 중 | 구독 중 전부 포함 | 열람·내보내기만 |
| 체험 `trial` | 0원 14일 | 포함 | 포함(로그인 필요) | 포함 | 열람·내보내기만 |

제안 이유: 영구에 웹을 무기한 주면 서버 원가가 무기한 발생한다(10장 4장 표 "영구와의 관계"). 웹 사용을 업데이트 유효 기간에 묶으면 기존 수익 구조(업데이트 연 갱신)와 일치한다. 영구 사용자의 핵심 가치(오프라인 영구 사용)는 유지된다.

- 업데이트 갱신 단위(제안): `updates_yearly`는 좌석 수만큼 과금하고 업데이트 유효 기간도 좌석 단위로 가진다(좌석 A만 갱신하면 B는 폴백). 수량 저장 위치는 Q11 ④와 함께 `팀장 결정 필요`.
- 판매 단위(확정 D-H1): 좌석(사용자) 단위. 라이선스 1개 = 사용자 1명(웹 + 설치형 PC 2대). 직원 추가는 좌석 추가 구매. `licenses`/`org_features`에 `seats` 컬럼을 **판매 시작 전 스키마에** 넣고, 조직 멤버에 좌석을 배정한다.
- 웹 전용 사용자와 영구(확정 D-H4): 판매하되 결제 화면에 "영구 = 설치형 영구 사용, 웹은 업데이트 기간 동안"을 명시하고 동의 체크를 받는다. 웹 전용이면 기간제·구독 권장 문구를 표시. 영구 만료 후 웹 읽기 전용에서도 폴백 상태의 AI 렌더 허용(`01_PRD.md` 4.3절)과 같은 동작이 되도록 맞춘다(제안). 만료 후에도 클라우드 → 로컬 내려받기는 허용(3.1절).
- 가격 자리: 영구 기존가 490,000/890,000원(`01_PRD.md` 4.1절)은 유지 가정. 기간제·연 구독 가격은 `미확정`(Q3). 숫자는 이 문서에서 정하지 않는다.
- 크레딧(AI·클라우드 법규 검토)은 상품 무관 별도 지갑으로 웹·설치형 공통(`01_PRD.md` 4.5~4.9절). 도면 0크레딧 원칙은 웹에서도 동일(순수 클라이언트 연산).

### 4.7 유효 권한 합성 규칙 (제안, R2·C2 해소)

원칙: 권한의 단위는 **사용자**다. 입력 = 그 사용자에게 배정된 좌석(`license_seats`, 소유 주체 `entitlement_source`: `license`=영구·기간제, `plan`=구독, `trial`=체험, `05_DATA_MODEL.md` 2.18) 중 평가 시각에 유효한 상품 집합. 고정 순위로 한 상품을 고르지 않고, **권리 하나하나를 상품별로 합성**한다(불리언 OR, 수치 최대값). 합산(2대+2대=4대)은 하지 않는다. 크레딧 지갑은 합성 대상이 아니다(조직 공통). **합성 범위**: 평가 대상 조직(요청의 세션 조직)의 `license_seats.org_id = 대상 조직`인 좌석만 합성한다. 같은 사용자의 개인 조직 좌석과 팀 조직 좌석은 서로 합성하지 않는다(조직 교차 금지). 서버 강제는 `05_DATA_MODEL.md` 2.18·2.20절.

상품 하나의 권리(`01_PRD.md` 4.3절과 같은 값):

| 상품 상태 | 웹 편집 | 설치형 편집 | 열람·내보내기 | AI 렌더 | 클라우드 검토·규칙 팩 | 기기 수 |
|---|---|---|---|---|---|---|
| 영구 + 업데이트 유효 | O | O | O | O | O | 2 |
| 영구 + 업데이트 만료(폴백) | X | O(마지막 자격 버전·팩) | O | O | X | 2 |
| 기간제 활성 | O | O | O | O | O | 2 |
| 구독 활성 | O | O | O | O | O | 2(D-H1) |
| 체험 14일 | O | O | O | O(가입 크레딧) | O | 1 |
| 기간제·구독·체험 만료 | X | X | O | X | X | - |

합성 예: 영구(업데이트 만료) + 구독 활성 → 웹 편집 O, 클라우드 검토 O, 기기 수 max(2,2)=2. 구독이 끝나면 영구 폴백 권리만 남는다. 설치형 라이선스 파일은 사용자·기기당 1개이며 `offline_valid_until`은 설치형 편집을 주는 상품 중 가장 늦은 것(영구 null)을 쓰되 그 상품 종료일로 clamp(D-H3). 권리 하나하나에도 만료가 있다: 파일의 `rights_expiry`(권리별 종료 시각. 영구가 주는 권리는 발급 + 30일 온라인 재확인, 확정 D-H5 ②·4.3절)를 두어, 구독이 준 권리가 영구 상품의 무기한 `offline_valid_until` 때문에 종료 후에도 로컬에 남지 않게 한다(권리별 종료 후는 그 권리 false). 필드 정의는 `04_API.md` 2.4절.

사용자별 상태 × 동작:

| 상태 | 웹 | 설치형 | 효력 시점 |
|---|---|---|---|
| 미배정(멤버, 좌석 없음) | 로그인·열람·내보내기·클라우드 내려받기만. 편집·저장·AI는 402 `entitled=false`(사유 `seat_unassigned`) | 활성화 불가. 로컬 파일 열기·내보내기만 | 배정 즉시 해제 |
| 배정 | 보유 상품 합성값 | 활성화 사용자당 PC 2대(D-H5 ③), 합성값 | 서버 즉시, 웹은 캐시 TTL(Q6), 설치형은 refresh 때 파일 재서명 |
| 회수 | 다음 요청부터 미배정과 같음(진행 중 저장은 402) | 그 좌석의 활성화 자동 해제(`revoke`). 온라인이면 다음 refresh에서, 오프라인이면 `offline_valid_until`·`rights_expiry`(영구 좌석도 최대 30일, D-H5 ②)까지 로컬 기능 유지(D-H3 위험 수용), 클라우드·AI는 즉시 불가 | 서버 즉시, 로컬 파일은 위 한도 |
| 재배정 | 새 사용자: 새 좌석 행, 이전 사용자: 회수와 같음 | 새 사용자 PC 2대 신규 활성화. 이전 사용자의 클라우드 프로젝트는 조직 소유라 남음 | 새 행 생성 시점. 재배정 제한(확정 D-H5 ②): 회수한 좌석은 7일 냉각 후 재배정(회수 기기의 온라인 해제 확인 시 즉시 가능), 좌석당 재배정 30일 2회. 위반 시 거부(`04_API.md` 7.1) |

## 5. 웹 엔진 번들 노출(판정 로직 공개) 위험과 대응

위험(10장 4장 표 B·A): 웹 번들에 판정 엔진이 그대로 실려 로직을 읽고 복제할 수 있다. 완전 차단은 불가능하다(브라우저에서 실행되는 코드). 방어는 "코드가 아닌 데이터·서버 기능에 가치를 둔다"이다.

| 대응 | 내용 | 상태 |
|---|---|---|
| 가치 이동 | 규칙 팩(법령 데이터)은 서버가 자격 확인 후 서명 URL로만 제공한다. 사실 정정: **팩은 체험에도 내려가며 브라우저에서 평문**이므로 팩 자체는 비밀이 아니다(복제 억제 효과는 최신성·서버 기능에 한정) | 기존 `eligible_rule_packs()`(`02_ARCHITECTURE.md` 2.2절) 웹에도 적용 |
| 팩 분리 | 팩을 엔진 패키지 밖(서버 배포 데이터)으로 분리. CI 번들 검사에 "엔진 번들에 팩 0바이트 포함" 추가 | 제안 |
| 서버 기능 | 클라우드 법규 검토·AI·렌더는 서버 크레딧 선차감 | 기존 |
| 소스맵 | 운영 소스맵 비공개, 최소화. 난독화는 보조 수단(우회 가능, 보호 아님) | 제안 |
| 무로그인 체험 | 허용 시 번들 노출 + 샘플 팩 제한 여부는 결정 필요(Q7). 10장은 "로그인 없이 체험"을 제안 | 미결 |
| 약관 | 역공학·재배포 금지 명시 | 제안, 법 검토 `미확인` |
| 잔여 위험 | 영구 라이선스 바이너리 패치 우회는 이미 수용(D-7, `09_SECURITY_PLAN.md` T-3). 웹 번들 복제도 같은 범주로 수용하되 규칙 팩 게이트로 완화 | 확정 필요(Q7) |

출처 분리·브라우저 방어(제안):

| 항목 | 규칙 |
|---|---|
| 출처 | `(studio)`는 별도 서브도메인(예 `app.`)으로 분리가 기본값. 마케팅 도메인과 쿠키·스토리지 분리. 같은 출처 유지는 예외로 팀장 승인 |
