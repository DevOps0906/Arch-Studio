## 2. 결정·발견

- [DECISION] 도메인 분리: JWT 서명 입력은 표준(JWS)이라 접두를 붙이면 PyJWT 검증이 깨진다. 대신 보호 헤더 `ctx`에 용도를 넣어 서명 대상에 묶고, 키·kid 분리를 생성 시 강제. 라이선스 입력(`arch-license-v1\n…`)과 JWS 입력(`eyJ…`)은 첫 바이트부터 다르다. 테스트로 교차 거부 확인.
- [DECISION] `feat`는 서버가 실행 행에서 정한다: intake `source='consult'` → `arch.intake_consult`(오픈소스 강제), proposal은 variant `proposal`만 서술 토큰(doc_template은 403).
- [DECISION] 잡 토큰 발급 조건에 실행 행 행위자(`created_by`)의 활성 멤버십 재확인 추가(P15). 잡 `created_by`가 있으면 실행 행과 같아야 한다.
- [DECISION] 업로드 경로의 `project_ref` 폴더는 `project_snapshot`에만(필수). `arch.cloud_projects.storage_path` CHECK(2400:231)가 `<local_id>/` 폴더를 요구하기 때문. 다른 목적은 `project_ref`를 받기만 하고 경로에 넣지 않는다(04_API의 `<org_id>/arch/<purpose>/<uuid>.<ext>` 형식 유지).
- [DECISION] 상한·목록 값(전부 제안): render_input png 10MB, proposal_sheet svg 2MB, project_snapshot `.arch` 100MB(버킷 상한), consult_audio m4a·webm·ogg·wav 200MB(형식 `미확인`), 워커 경로 600회/분, 잡 조회 사용자 120회/분, 결과 서명 URL 300초, 워커 키 최소 32자.
- [DECISION] ai-token 응답은 봉투 `{ ok, data: { token, expires_at } }` + 최상위 `token`(워커 `job-token.ts`가 `body.token`을 읽음, 워커는 소유 밖). 
- [FINDING] Supabase 서명 업로드 URL 수명은 서버 고정(2시간)이라 짧게 할 수 없다. `upsert=false` + 경로마다 새 UUID + `expires_at`은 Storage 토큰 exp를 그대로 알림. 사용 시점 재검사(크기·MIME·매직바이트·조직 폴더·sha256)는 소비 경로(render·proposal·cloud-projects·voice 작업)의 몫이고, 신고 `sha256`을 보관할 테이블이 없어 지금은 형식만 검사한다.
- [FINDING] 교차 언어 확인(수동, 스크래치패드 스크립트): TS `createAiTokenSigner`로 만든 잡·사용자 토큰을 `apps/api` `verify_token`(JWKS = `publicJwk()`)이 통과시키고 `job`·`run`·`feat`·수명 300을 읽었다.
- [FINDING] 방어 제거 변이 26건 중 25건 테스트 실패(KILLED). 남은 1건(업로드 확장자 1차 검사만 제거)은 조립 후 재검사가 같은 결과를 내는 이중 방어라 살아남음 → 두 층을 함께 제거하면 실패 확인.
- [FINDING] `apps/api` 변경은 `app/auth/**` 외에 `app/routes/graphs.py` 호출 2줄이 필요했다(본문 run_id·조회 실행 job_id는 라우트만 안다). 검사 로직은 `app/auth/deps.py`에 두고 라우트는 호출만 한다.

## 4. 통합 테스트 목록(로컬 Supabase 없음, 미실행)

1. `start_ai_run`(service_role) → 같은 request_id 2회 호출 시 원장 1행·실행 1행, 반환 credits = `pricing.ts` 값(variant 8종).
2. `start_ai_run`을 authenticated JWT로 호출 → 42501(EXECUTE 없음).
3. ai-token: `claim_jobs`로 running이 된 `arch.review` 잡 → 200, `complete_job` 후 → 409, `fail_job` 후 → 409.
4. ai-token: 다른 조직 실행 행이 같은 job_id를 가리키는 비정상 데이터 → 404.
5. ai-token: 실행 행 행위자를 `org_members.status='suspended'`로 바꾼 뒤 → 403.
6. uploads/sign: 반환 URL로 PUT 성공, 같은 URL 두 번째 PUT 거부(upsert=false), 다른 경로로 PUT 불가.
7. uploads/sign 경로가 `arch.valid_user_path`·`cloud_projects` CHECK를 통과(`save_cloud_project`에 그대로 넣어 성공).
8. jobs/{id}: 조직 A 사용자가 조직 B 잡 id → 404, RLS로 실행 행도 0행.
9. jobs/{id}: 렌더 성공 잡 → `org-files` 서명 URL로 내려받기 성공, 300초 후 실패.
10. 워커(`workers/arch-jobs`) → ai-token → FastAPI `POST /graphs/arch.review/runs`(같은 토큰 재사용 401, 다른 run_id 403).
