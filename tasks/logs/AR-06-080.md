# AR-06-080 설치형 PNG 래스터화: Rust resvg 명령 `rasterize_svg`·shell-bridge `Rasterizer`

- 위험도: 높음(새 Tauri 명령·권한, 화면이 준 SVG 문자열을 래스터화 = 외부 입력 처리)
- 근거: `06_AGENT_PLAN.md` AR-06-080 행(10장), PRD D-35·D-36, `packages/drafting/src/writers/png/README.md`(022 렌더 옵션·재현 방법), `tasks/logs/AR-06-022.md`, `.claude/rules/desktop.md`, `tasks/logs/AR-06-{005,041}.md`(오류에 원문 없음·입력 상한·명령 3곳 일치).

## 선행 검증(가장 먼저): 업스트림 crates.io resvg ↔ resvg-js 2.6.2 골든

환경: Linux x86_64, rustc 1.97.0, 스크래치 크레이트(저장소 밖). GitHub(`zimond/resvg` 포크 소스)은 이 환경에서 프록시 403이라 포크 diff는 직접 볼 수 없었다. 대신 crates.io 업스트림으로 렌더해 결과로 판정했다.

| 조합 | 크기 | 픽셀 | PNG 바이트 |
|---|---|---|---|
| resvg 0.34.0(업스트림, `default-features=false, features=["text"]`) + usvg 0.34.1 + tiny-skia 0.10.0 + fontdb 0.14.1 + rustybuzz 0.7.0 + **png 0.17.16**(최신 해석) | 3건 일치 | **3건 모두 0 화소 차이** | 다름(51,890B vs 16,484B 등 — png 크레이트 압축·필터 기본값 변경) |
| 위 + **png `=0.17.5`**(022가 기록한 resvg-js 내장 버전) | 3건 일치 | **0 화소 차이** | **3건 모두 바이트 동일**(sha256이 `meta.json`의 `png_sha256`과 같음) |

- 크기 계산(포크와 같게 맞춘 것): 정수 크기 경로(`tree.size.to_int_size().scale_to_width()`, ceil)는 세로가 1px 크다(840×595, 600×425 vs 골든 594·424) → 불일치. **부동소수 크기**: `h = round(w × size.h / size.w)`(f32), 변환 = `scale(w/size.w, h/size.h)`(축별) → 3건 모두 0 화소 차이. 균일 배율 `scale(s, s)`는 4~9,586 화소 차이(최대 채널 차 96)라 폐기.
- PNG 바이트: 골든 IDAT는 모든 행 필터 Sub(1)·zlib `789c`(기본 압축) = png 0.17.5 기본값. png 0.17.16은 기본 필터·압축이 달라 바이트가 다르다(픽셀은 같음). `png = "=0.17.5"`로 고정하면 바이트 동일.
- 결론: **포크 패치는 이 입력(writeSvg 출력·번들 글꼴·022 옵션)의 렌더 결과에 영향이 없다.** 업스트림 resvg 0.34.0으로 골든과 **바이트 동일**. 허용 오차 기준(채널 차 3 초과 화소 0.1% 미만)은 완화하지 않았고, 다른 아키텍처 대비 안전망으로만 남긴다(아래 테스트).
- 성능(릴리스, 4코어): A3 2480×1754 렌더 20ms·전체(인코딩 포함) 95ms, 최대 상한 근처 11900×8415(1.0억 화소) 렌더 0.49s·전체 4.3s(대부분 deflate).

### 방어 없는(수용) 항목
- R8 시간 제한 뒤에도 작업 스레드는 끝까지 계산한다(resvg 취소 불가). 상한(8MiB·노드 50만·1억 화소) 안에서 악성 입력이 수 분 CPU 1코어를 쓸 수 있고, 그동안 PNG 명령은 `BUSY`. 앱 재시작으로 회복. 공격자 전제(웹뷰 XSS)는 이미 사용자 데이터에 닿는 권한이라 이득이 작다.
- R1·R2 IPC 역직렬화 전 크기 제한은 Tauri가 하지 않는다(다른 명령과 같음). 8MiB 검사는 문자열을 받은 뒤다. TS 어댑터가 보내기 전에 먼저 막는다.
- 최대 상한(1억 화소) 렌더의 최대 메모리 ≈ Pixmap 400MB + png 필터 버퍼 약 400MB + 결과. 저사양 PC(8GB)에서도 견디지만 크다 — 화면은 미리보기에 작은 폭을 쓰도록 안내(후속 화면 작업).

## [DECISION]
- D1 **렌더러 = crates.io 업스트림 resvg 0.34.0**(포크 아님). 선행 검증에서 골든과 바이트 동일이므로 `[patch]`로 포크를 끌어오지 않는다(GitHub 소스 의존 없음). 렌더 크기 계산은 resvg-js 포크와 같게 f32 비율·축별 배율로 직접 구현.
- D2 `png =0.17.5` 고정(바이트 일치 조건). 보안 패치 등으로 올리면 골든 바이트 비교가 깨지므로 화소 허용 오차로 바꾸는 결정과 함께 한다(기준 완화 아님 — 022 설계의 "환경이 다르면 화소 비교").
- D3 입력 상한 8 MiB·노드 50만·출력 1억 화소(022)·결과 100 MiB(export 상한)·제한 시간 30초·동시 1건. 상한 초과 = AR055, 렌더 실패·시간 초과 = AR056(04_API에는 "PDF 생성 실패"로만 적혀 있음 — PNG도 포함하도록 **04_API 7.3 문구 갱신 필요, docs 소유 밖**), 허용 밖 요소·DTD·깨진 SVG = INVALID_INPUT, 진행 중 = BUSY(화면 흐름 코드).
- D4 요소 허용 목록은 현재 writeSvg 출력 기준이다. 작성기가 새 요소(그라디언트·clipPath·image 등)를 쓰게 되면 이 명령이 INVALID_INPUT으로 거부하므로 **작성기 변경 시 raster.rs 목록·골든을 함께 갱신**해야 한다(022·작성기 소유자 공지).
- D5 `dpi` 옵션의 폭 = round(SVG px ÷ 96 × dpi). 022 `writePng`는 용지 mm에서 계산하므로 .5 경계에서 1px 다를 수 있다 — 정본 비교는 `widthPx`로 한다.
- D6 글꼴 정본 경로(`packages/drafting/fonts`)를 `include_bytes!` 상대 경로로 참조(복사본 없음, sha256 테스트). src-tauri 단독 체크아웃으로는 빌드되지 않는다(모노레포 전제).
- D7 `PlatformAdapters.rasterizer`는 선택 필드(필수로 하면 072 웹 팩토리가 깨짐). capability 키는 추가하지 않았다(키 집합 고정 계약 유지) — 필요하면 072와 합의 후 `rasterize` 키 추가.

### 남은 한계(수용·후속)
- **시간 초과 뒤에도 작업은 계속된다**: resvg는 취소가 없어 30초 제한은 명령 응답만 끊는다. 작업 스레드는 끝까지 돌고 그동안 PNG 명령은 `BUSY`. 이번 예산은 그 시간을 상한(≈수 초)으로 묶는 완화책이지 차단이 아니다 — 예산이 덮지 못한 비용 경로(예: 미지의 usvg 초선형 경로)가 있으면 같은 문제가 남는다. 코드 주석(`raster.rs` 모듈 머리·`RENDER_TIMEOUT`·`rasterize_guarded`)에 명시.
- **후속(근본 대책)**: 렌더를 별도 sidecar 프로세스로 옮기고 시간 초과 시 프로세스를 끝낸다(메모리 상한도 OS가 강제). 새 바이너리·capability·서명·업데이터 영향이 있어 별도 작업(위험도 높음)으로 계획 필요 — 06_AGENT_PLAN 행 추가 제안(docs 소유 밖).
- 문서 제안: 04_API 7.3 AR055 설명에 "PNG 래스터화 입력 비용 예산(요소 깊이·글자·tspan·대시)" 포함, PRD 보안 절 R8에 "시간 초과 = 응답만 끊음" 한계 명시(docs 소유 밖).
- 작성기(writeSvg)가 tspan·긴 문단·촘촘한 대시를 쓰게 되면 이 예산에 걸릴 수 있다 → 작성기 변경 시 raster.rs 예산·골든을 함께 검토(D4와 같은 공지).
- 깊이 경계 32에서의 실제 스택 사용은 측정하지 않았다(32단 렌더는 기본 스택·테스트 스레드에서 통과).
