### 1. 구성 권고
- **렌더: (a) 매스마다 mesh 1개**(정적 맥락 — 대지·주변·엔벨로프 — 은 따로). 근거:
  - CPU 측 비용 차이가 작다. S200k(매스 50·삼각형 20.4만)에서 `gl.render` CPU 시간 (a) 52 드로우콜 중앙 0.9ms·p95 3.0ms, (b) 병합 3 드로우콜 0.4/0.5ms. 16ms 예산에서 무시할 수준.
  - 편집 친화: 매스 하나를 고치면 그 매스 버퍼만 바꾼다. (b)는 편집마다 병합 버퍼 전체(3.7MB)를 다시 만들고 올린다.
  - 선택: 개별 mesh는 three의 바운딩 구 사전 걸러냄 덕분에 BVH 없이 레이캐스트 중앙 0.2ms·p95 1.1ms. 병합 20만 삼각형은 BVH 없이 14ms/121ms라 BVH가 필수다(빌드 139ms, 그 뒤 0.1ms 미만).
  - 소프트웨어 GL에서는 (a)가 가장 빨랐다(4.4fps vs 1.1fps). 화면 밖 매스를 절두체 컬링으로 건너뛰기 때문이다. 실제 GPU에서는 차이가 작을 것으로 본다(미확인).
  - (c) InstancedMesh는 쓰지 않는다. 매스마다 바닥 모양이 달라 인스턴싱할 대상이 없다. 같은 모양 50개라고 가정해도 이득이 없었다.
  - 윤곽선에 `EdgesGeometry`는 쓰지 않는다. 20만 삼각형에서 생성이 2.17초 걸렸다. 윤곽은 DesignModel 데이터(바닥 변 × 층 경계)로 바로 만든다.
- **Manifold는 엔진 워커(engine.worker)에서 돌린다.** 메인 스레드에서는 돌리지 않는다. 근거:
  - 전체 불린은 프레임 예산을 넘는다. 매스 50(12각형) ∩ 엔벨로프는 Node 43ms·브라우저 워커 46ms, 엔벨로프 − 매스는 53/57ms. S200k는 1.1~1.4초.
  - WASM 초기화는 싸다. Node 첫 회 21ms(이후 8ms), 브라우저 워커 54ms, 메인 스레드 36ms. 그래서 위치를 정하는 기준은 초기화가 아니라 연산 시간이다.
  - 워커 결과는 Transferable `ArrayBuffer`로 넘긴다. 20만 삼각형(3.7MB) 왕복이 전송 중앙 3.7ms인 반면 구조적 복제는 21.9ms다. Node worker_threads에서는 0.09ms 대 7.1ms였다.
- **드래그 중 증분 방식**:
  - 렌더 쪽: 움직이는 매스는 mesh 위치(행렬)만 바꾼다. 지오메트리 재생성과 불린은 하지 않는다(translate + getMesh도 0.1~0.7ms).
  - 판정 쪽: 매 프레임 워커 `judge` 레인에 최신만 유효(seq)로 보낸다. 응답을 기다리는 동안에는 새 요청을 보내지 않고 마지막 값으로 합친다. 워커는 **움직인 매스 1개 − 엔벨로프**(초과분 표시)만 계산하고 나머지 매스 결과는 캐시한다.
  - 측정: 매스 1개(12각형·5층) 5.7ms, p95 9.1ms(Node, ∩·− 둘 다). 브라우저 왕복 지연은 중앙 7.8ms·p95 40ms(SwiftShader와 CPU를 나눠 쓴 상태). 엔벨로프를 드래그 시작 때 매스 주변 상자로 한 번 잘라 두면 −35%(`bench:crop`).
  - 전체 재계산(엔벨로프 − ∪매스: 남은 용량 표시)은 드래그 끝(pointerup)에 한 번만 한다. S50 전체 121ms·p95 174ms.
  - 판정 수치(건폐·용적·높이)는 불린이 필요 없는 rules 경로라 따로 판정 p95 200ms 예산 안에서 돈다. 불린은 화면 표시용이다.
- **매스 솔리드는 `extrude(전체 높이, nDivisions = 층 수 − 1)` 1회로 만든다.** 층마다 extrude한 뒤 union하면 20~70배 느리다(S50 203ms 대 9ms, S200k 15.5초 대 0.22초). DesignModel v1의 층은 매스 바닥 하나를 공유하므로 층고가 모두 같을 때 그대로 쓸 수 있다. 층고가 다르면 그 층들만 union하거나 extrude를 높이 구간별로 나눈다.
- **정수 정규화(`canonicalMesh`·`closeMesh`)는 드래그 경로에서 빼고 렌더는 `getMesh()` Float32 버퍼를 그대로 쓴다.** 정규화는 S50에서 32ms, S200k에서 2.7초 걸린다. 결정적 바이트가 필요한 곳(도면·스냅샷·내보내기)에서만 쓴다.
- **실행 취소 100단계: 불변 DesignModel + 구조 공유 이력(모델 참조 100개) + 명령 라벨.** 근거(매스 50개 모델, JSON 29KB):
  - 매스 1개 이동 100단계 힙: JSON 스냅샷 5.5MB, structuredClone 9.1MB, 구조 공유 156KB, 명령(역연산) 69KB.
  - 매스 50개 동시 이동 100단계 힙: 구조 공유 5.0MB, 명령 92KB.
  - 기록 시간은 모두 1ms 미만이고 되돌리기는 참조 교체 O(1)이다.
  - 명령 패턴은 메모리가 가장 작지만 역연산 버그 위험이 있다. 구조 공유로도 100단계 상한에서 충분하므로 단순한 쪽을 고른다.
  - 340각형 매스라면 모델이 약 10배 커지지만 구조 공유는 바뀐 매스만 보관하므로 문제없다.
- **CSP·보안**:
  - 데스크톱 CSP(`script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; style-src 'self'`)를 preview 응답 헤더로 걸고 측정했다. 위반 0건이다. Manifold WASM은 워커와 메인 스레드 양쪽에서 동작한다.
  - 워커는 `new Worker(new URL('./x.worker.ts', import.meta.url), { type: 'module' })`로 만든다. Vite가 별도 파일로 내보내므로 blob:이 없다.
  - 빌드 산출물 점검 결과: `eval(` 0건, `new Function` 0건, `@img/sharp` 0건(AR-06-016 확인 조건 충족, 하니스 dist 기준), 인라인 script 0건. `blob:`은 문자열 비교 1건뿐이다(URL 프로토콜 검사이고 생성이 아니다).
  - **drei `Text`(troika-worker-utils)와 three-stdlib `DRACOLoader`는 `URL.createObjectURL`로 blob 워커를 만든다.** 쓰면 `worker-src blob:` 완화가 필요하므로 금지한다. 글자는 DOM 오버레이나 SDF 없는 방식으로 만든다.

### 2. 지오메트리 단순화 방침
- 현재 데이터 모델(다각형 바닥 × 층)의 실제 규모는 매스 50개가 7천 삼각형(12각형) 수준이다. 20만 삼각형은 곡선 근사 바닥(340각형) 같은 극단 상한이다. 실기에서 최소 사양 30fps를 넘으면 단순화는 하지 않는다.
- 실기 미달 시 아래 순서로 적용하고, 단계마다 하니스로 다시 잰다. 모두 **표시 전용**이다. 판정·도면·면적은 원본 정수 기하로 계산하므로 결과가 바뀌지 않는다(LLM 좌표 생성 없음, 결정적 함수).
  1. L1 채움 비용: DPR 상한 1(최소 사양), MSAA 끄기, 반투명 엔벨로프 단일 패스(`side: FrontSide` 또는 forceSinglePass). DoubleSide 투명은 2패스라 엔벨로프 삼각형이 두 번 그려진다.
  2. L2 정적 병합: 선택·편집 중이 아닌 매스를 매스 10개 단위 청크로 병합해 드로우콜을 줄이고, 청크마다 BVH를 둔다. 윤곽선은 끈다.
  3. L3 표시용 바닥 단순화: 꼭짓점이 64개를 넘는 바닥은 표시에만 Douglas–Peucker(허용 50mm)를 쓰고, 장면 상한은 20만 삼각형으로 둔다. 상한을 넘으면 화면에 "표시 단순화 중" 배지를 띄운다.
  4. L4 드래그 중 저해상도: 드래그하는 동안만 DPR 0.75와 그림자·윤곽 끄기(drei `PerformanceMonitor`·`AdaptiveDpr` 계열을 쓰되 blob을 쓰지 않는 것만).

### 4. 이 환경에서 확인하지 못한 것
- **실제 GPU 프레임레이트**(최소 사양 RAM 8GB·WebGL2 30fps, 권장 60fps)는 사람이 실기에서 측정해야 한다. 이 환경의 WebGL2는 SwiftShader다.
  - 방법: `spikes/modeler-perf/README.md`. `pnpm install --ignore-workspace && pnpm build && pnpm preview` → http://localhost:4173 → [렌더 측정] → [JSON 복사] → 아래 "실기 측정 기록"에 PC 사양과 함께 붙인다.
  - 판정: S200k의 (a) 개별 행이 최소(평균 30fps 이상, p95 40ms 이하)와 권장(평균 57fps 이상, p95 20ms 이하)을 넘는지 본다.
- WebView2(Tauri) 안 동작: 이번에는 Chromium 브라우저에서만 쟀다. WebView2도 Chromium 계열이지만 GPU 가속 정책과 CSP 실제 적용은 T-001/AR-06-071 경로에서 확인한다.
- `deviceMemory`가 8GB 상한이라 RAM 8GB PC에서의 메모리 압박(탭 폐기 등)은 실기에서 작업 관리자로 본다.
- GPU 타이머 쿼리(EXT_disjoint_timer_query_webgl2)로 GPU 시간을 따로 재는 것은 하지 않았다. rAF 간격만 잰다.
