## 1단계 구현 (glTF·IFC 내보내기)
- glTF(`exportGltf`): mm→m, Z-up→Y-up((x,y,z)→(x,z,-y), 회전이라 감김 유지), Math.fround, POSITION min/max, 면별 정점 분리+면 법선, 인덱스 없음, 고정 generator, 단일 버퍼 data URI.
- IFC4(`exportIfc`): Project·UnitAssignment(mm)·GeometricRepresentationContext(+Body 서브컨텍스트)·Site·Building·Storey·RelAggregates×3·ContainedInSpatialStructure, 매스 = IfcBuildingElementProxy + IfcTriangulatedFaceSet.
  GlobalId = FNV-1a 128(project_id + "\0" + 요소 키) → IFC base64 22자. FILE_NAME 시각·OwnerHistory.CreationDate = 입력 `timestamp`(유닉스 초, 없으면 0).
- 골든: `src/gltf/golden/box.gltf`, `src/ifc/golden/box.ifc`(갱신 `GLTF_GOLDEN_UPDATE=1`·`IFC_GOLDEN_UPDATE=1`).
- web-ifc 왕복 관찰: 형상을 중심 기준으로 옮기고 변환 행렬에 0.001(mm→m)·Y-up·이동을 담는다 → 이동값이 glTF 결과(중심 (5,1.5,-4)m)와 일치.
- 남은 것: 무료 IFC 뷰어 수동 점검 기록(사람 판정), .3dm 내보내기·가져오기(다음 단계), 압축 해제·시간 상한(가져오기 단계).

## 리뷰 반영 (2026-11-01)
- 리뷰 반영: IFC 문자열 BMP 밖 문자는 X4(8자리 16진), 짝 없는 서로게이트는 U+FFFD로 바꿨다(골든 `src/ifc/golden/emoji-name.ifc`, web-ifc 왕복 확인). exportIfc·exportGltf는 safe int가 아닌 꼭짓점이 오면 RangeError를 낸다.
- 좌표 기준 판단: 매스 좌표는 **대지 로컬 원점 기준**이 보장된다. 근거는 `packages/domain/src/units.ts`의 `MM_COORD_LIMIT = 10_000_000`(로컬 원점 기준 ±10km, mmSchema가 거부)와 `packages/geometry/src/validate.ts`의 COORD_LIMIT(OUT_OF_RANGE). 솔리드 커널도 이 상한 안을 전제로 한다(kernel.ts: |v| ≤ 2^24에서 float32 정확).
  절대 TM 좌표(수억 mm)는 들어올 수 없어 코드를 바꾸지 않는다. glTF float32(m)의 최악 오차는 ±10km 끝에서 반 ULP ≈ 0.5mm(8192~16384m 구간 ULP 2^-10m)이고, 4km 안에서는 0.12mm 이하라 표시용으로 충분하다. IFC는 정수 mm를 그대로 쓰므로 오차가 없다.

## 2단계 결정성 스파이크 (.3dm, rhino3dm 8.35.0) — 2026-11-01
- 방법: 같은 메시 1개를 같은 인스턴스·2초 간격·새 인스턴스로 내보내 바이트 비교(7,970바이트 파일).
- 결과: **바이트 불일치(46바이트)**. 원인 2가지.
  1. `ObjectAttributes.id`가 embind 읽기 전용(`BindingError: ObjectAttributes.id is a read-only property`) → 객체 id를 지정할 수 없고 저장 때 무작위 UUID(16바이트 + 그 청크 CRC).
  2. 파일 시작 절·속성에 저장 시각(`created`·`lastEdited`, 읽기 전용, wasm이 시계를 직접 읽음)·`revision`이 들어감.
- 확인(스크래치 전용): `Date.now`를 고정하면 시각 차이는 사라지지만 UUID는 남음(난수원이 `crypto.getRandomValues`도 아님). 전역 시계·난수 바꿔치기는 엔진 규칙 위반이라 채택하지 않음.

## [DECISION] AR-06-039 .3dm 골든 — 2026-11-01 (사용자 승인 방침에 따른 하향)
- 결정: .3dm만 **바이트 골든 대신 "의미 동일" 골든**(`src/rhino/golden/box.semantic.json`: 단위·객체 수·이름·키·id·닫힘·정점/삼각형 수·메시 해시 FNV-1a 64). glTF·IFC는 바이트 골든 유지.
- 이유: 위 스파이크 — rhino3dm은 객체 id 지정 불가 + 저장 시각을 내부에서 읽음. 같은 입력 → 같은 바이트를 만들 공개 API가 없다.
- 결정적 식별자는 사용자 문자열에 둔다: `arch_studio.id` = hash(project_id + 키) UUID(ifcGuid와 같은 FNV-1a 128을 8-4-4-4-12로), `arch_studio.key` = 매스 키. 다시 가져오면 `source_key`·`source_id`로 돌아온다.
- 갱신: `RHINO_GOLDEN_UPDATE=1 pnpm --filter ./packages/io test`.

## 2단계 구현 (.3dm 내보내기·가져오기)
- 구성: `src/rhino/{index,export,import,limits,errors,module}.ts`. `load3dmKernel({ wasmBinary })`(비동기) → `kernel.export3dm`·`kernel.import3dm`(동기)·`memoryBytes()`. wasm 바이트는 호출자가 넘긴다(엔진 fetch 금지). Emscripten `instantiateWasm`로 직접 인스턴스화해 선형 메모리를 잡는다.
- embind 래퍼는 finally에서 지운다. `File3dmObjectTable.delete(id)`처럼 이름을 덮어쓴 클래스가 있어 기본 `ClassHandle.prototype.delete`를 직접 부른다(3,000회 왕복 뒤 메모리 증가 0 확인).
- 가져오기: 입력 크기(20MB, AR055) → 호출 전 메모리 상한 → `File3dm.fromByteArray` → 메모리 상한(512MB)·증가량 ≤ max(입력×10, 64MB)(R3DM_DECOMPRESSION_LIMIT) → 단위(지원 8종, None·Custom·Unset 등은 needs_unit/AR053) → 객체 수(1만)·꼭짓점(200만)·면(400만) 상한 → mm 환산 후 ±COORD_LIMIT·roundHalfAway 정수화 → 사각형 면 분할 → canonicalMesh → 후보(needs_confirmation, closed 여부). 메시 아닌 객체는 AR054 경고(종류별 개수). 상한은 options.limits로 낮추기만.
  wasm 트랩(RuntimeError)·메모리 상한은 `discard_kernel: true` — 호출자가 커널을 버리고 다시 로드한다.
- **호출 쪽(앱) 책임**: rhino3dm은 동기 wasm이라 함수 안에서 시간을 끊을 수 없다. 앱은 import3dm을 **워커에서** 돌리고 **시간 상한 초과 시 terminate** 해야 한다. 퍼징 실측: 손상 입력 하나가 메모리 증가 없이 9.1초 CPU를 썼다. 메모리 상한도 "호출 뒤" 검사라 실제 차단은 워커 격리가 맡는다.
- 퍼징: `src/rhino/fuzz.test.ts`(dxf-import 패턴, mulberry32 시드 고정 2,000건, 약 60초). 앱처럼 워커 + 건당 500ms 상한으로 돌리고 상한 초과는 수만 기록한다.
  결과: 성공 425 · 오류 1,492(MALFORMED 1,480 · EMPTY 10 · MEMORY_LIMIT 2) · 시간 초과 83 · 커널 재로드 2 · **INTERNAL 0**. (2초 상한 3,000건 시험 때는 WASM_TRAP 1·MEMORY_LIMIT 3·시간 초과 186.)
  관찰: 수 KB 손상 파일이 wasm 메모리를 512MB 넘게 키운 사례가 있다 → 메모리 상한 검사가 실제로 걸린다. 다만 호출 뒤 검사라 앱 워커의 메모리·시간 상한이 1차 방어다.
- wasm 실측: `rhino3dm.wasm` 2,670,316바이트(gzip -9 1,042,560), JS 글루 126,991바이트, 초기 선형 메모리 17,367,040바이트.
