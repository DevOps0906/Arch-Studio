## 0. 계획 공격 (착수 전)

전제: 토큰 발급자는 web 서버(AR-06-047)이고 이 서비스는 **공개키(JWKS)로 검증만** 한다. 잡 토큰 = `sub=job:<job_id>`, scope 하나, `jti` 1회.

남는 위험(이 작업 범위 밖, 후속):
- `jti` 저장소는 프로세스 메모리다. 다중 인스턴스 배포 전에 공유 저장소(DB `core` 테이블 또는 Redis)로 바꿔야 재사용 방지가 성립한다 → 배포 작업에서 확정.
- 잡이 `running`인지 이 서비스가 다시 확인하지 않는다(발급자 047이 보장). DB 연결이 생기면 `core.jobs` 상태 재확인 추가.
- 레이트 리밋은 web 게이트(047)가 1차. 이 서비스 자체 리밋은 후속.

## 1. 결정·발견

- [DECISION] 검증 키 주입: `AI_TOKEN_JWKS_URL`(문서 8장 이름, https만) 또는 `AI_TOKEN_JWKS`(인라인 JWKS, 제안 이름) 중 정확히 하나. 둘 다 없거나 둘 다 있으면 기동 거부. 키는 제품 `arch`에 묶인다.
- [DECISION] 401 응답 본문은 사유를 나누지 않는다(`UNAUTHORIZED`). 사유 코드(`TOKEN_EXPIRED` 등)는 로그에만. 403은 `SCOPE_MISMATCH`·`JOB_TOKEN_REQUIRED`를 돌려준다(유효한 토큰 보유자에게만 보임).
- [DECISION] 그래프 경로 본문은 `{ run_id: uuid }`만(payload에는 id만, 02장 4절). 같은 (org, graph, run_id) + 같은 잡 재요청은 같은 실행을 돌려주고(재시도 재개), 다른 잡이면 409. `arch.layout`(P2)은 비활성 → 404.
- [DECISION] `GET /graphs/runs/{id}`는 jti를 소비하지 않는다(폴링). 시작 경로만 1회 소비.
- [FIX] 동치 코퍼스가 pydantic 쪽 결함 2건을 잡았다: (1) 선택 필드 null 거부를 BeforeValidator로 걸면 안쪽 검증이 파이썬 모드로 바뀌어 `holes`·`building_line`·`section_line`(strict 튜플)이 유효 입력을 거부 → `Strict._optional_not_null`(after, `model_fields_set`)로 교체. (2) `Literal[1]`이 `true`를 받는 파이썬 함정 → 정확 일치 검사. zod 쪽은 코퍼스 기대와 모두 일치(결함 0).
- [FINDING] `packages/domain`에 intake·review·layout 결과 zod가 없다. pydantic은 04_API.md 4.2·4.3·4.6절 기준으로 만들고 `PENDING_ZOD`로 표시. 문서 밖에서 더한 제약(zod에도 같은 값 필요): review `sentences[].source_ids` 최소 1(AR033), `source_ids`는 `sources[].id`에 있어야 함·id 중복 금지, intake `target_area_m2`가 있으면 `area_evidence` 필수(AR032), 길이 상한은 UTF-16 코드 단위(zod `.max()`와 같은 기준). 제안만(미적용): `target_area_m2 > 0`, 배열 개수 상한.
- [FINDING] 문서 계약 차이 없음(DesignModel·JudgmentResult·SheetSpec·DraftingProfile 구조 비교 통과).
