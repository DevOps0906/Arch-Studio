### 존재 여부 누출 정책 결정 (A11)
- 04_API.md 2.1·7.1절이 `AR002` 404(시리얼 무효)와 `AR006` 403(다른 조직)을 별도 코드로 정의했으므로 **구분을 유지**한다.
- 근거: (1) 시리얼 100비트 무작위라 존재 확인 오라클로 열거할 수 없다(10회/시간이면 사실상 0). (2) AR006을 받는 사람은 이미 유효한 전체 시리얼을 가진 사람이라 새로 얻는 정보가 "다른 조직 소유" 1비트뿐이고, 고객지원 안내(조직 전환·양도 D-8)에 필요하다. (3) DB 판정 순서상 비멤버는 AR003(정지·환불)을 볼 수 없다.
- 위험 수용: 유출된 시리얼을 가진 제3자는 "유효함"을 알 수 있다. 통일이 필요하면 `errors.ts`의 매핑 1줄(AR006 → AR002 404)로 바꿀 수 있다.

## 결정·구현 메모
- 정준화: `packages/drafting/src/sheet/hash.ts` `canonicalJson`과 같은 규칙(키 UTF-16 코드 단위 정렬, 공백 없음, undefined 칸 제외, -0 → 0, 비유한 수 RangeError) + 일반 객체 외 값 거부. 패키지 의존성을 늘리지 않으려고 `server/licenses/canonical.ts`에 같은 규칙으로 둔다(`packages/rules`의 2칸 들여쓰기 형식과는 다름: 04_API 2.4 "공백 없음"이 정본).
- 파일 형식: `{ payload: base64url(canonical UTF-8), sig: base64url(Ed25519(payload 바이트)), kid }`. 검증자는 payload 바이트에 대해 검증 후 JSON 파싱, `payload.kid === file.kid` 확인.
- `issued_at`은 초 단위 RFC 3339(`YYYY-MM-DDTHH:MM:SSZ`). `offline_valid_until`: `license` 출처 null, `plan` 출처 `min(issued_at + 7일, trial_ends_at)`(구독 종료 시각은 `org_features`가 주지 않아 7일만). 상품 3종 합성(`rights`·`rights_expiry`·`seat_id`, 기간제 종료일 clamp)은 AR-06-074/074a 소유: `PayloadExtension`으로 주입받는 확장점만 둔다(없으면 필드 생략).
- 멱등: 04_API 1장대로 자연 키. 활성화 `(license, device_hash)`, 플랜 `(org, device_hash)`는 DB가 기존 행 반환, 해제는 이미 해제면 그대로 반환, refresh는 읽기 + 재서명(부작용 없음). 별도 멱등 저장소 없음.
- 레이트리밋 저장소: `RateLimitStore` 인터페이스 + 기본 메모리 구현(고정 창, 항목 상한). **후속**: Vercel 다중 인스턴스에서는 인스턴스별로 따로 세므로 운영 전 `core.rate_limit_hit`(service_role) 또는 Redis 구현으로 교체 필요.

## 통합 테스트 (skip: 로컬 Supabase 없음, 2026-10-29)
단위 테스트는 `LicenseDeps` 목으로 서버 로직만 검증했다. 아래는 로컬 Supabase(`supabase start` + `pnpm test:rls`)에서 실제 RLS/RPC로 돌려야 할 시나리오:
- S1 activate(시리얼): 실제 `issue_license` 시리얼 → 정규화 해시가 `serial_hash`와 일치, 같은 기기 재호출은 같은 activation id(멱등)
- S2 AR006: 다른 조직 사용자 JWT로 활성화 → 403, 활성화 행 0
- S3 동시성: 같은 라이선스(max 2)에 서로 다른 기기 4개 동시 activate → 정확히 2개 성공, 2개 AR001. 플랜(체험 max 1) 동시 2개 → 1개 성공
- S4 AR003: `suspended`·`refunded` 라이선스 → 403, 비멤버는 AR003이 아니라 AR006
- S5 셀프 해제: owner JWT로 4회 해제 → 4번째 AR004, `self_deactivations_30d` 3. member JWT → 42501. 다른 조직 activation_id → P0002
- S6 refresh: `device_hash` 다름·해제됨·다른 조직 → 404, 라이선스 정지 후 refresh → 403
- S7 RLS: authenticated로 `license_activations.device_hash`·`licenses.serial_hash` SELECT 거부(컬럼 GRANT 없음), `activate_license`·`activate_plan_device` EXECUTE 거부(42501)
- S8 `org_features`: 비멤버 조직 42501 → refresh 404로 숨김
- S9 스키마 모드: `SUPABASE_DB_SCHEMA=core`(arch.*)와 `public`(모놀리스) 양쪽에서 RPC 이름 해석

## 미해결·요청
- **C-3(T-C4) 서명 키 규격 미결**: 09_SECURITY_PLAN.md S-4 "C-3 승인 전 AR-06-040 머지 보류 검토". 키 형식은 PKCS#8(PEM 또는 base64 DER)로 가정, `kid` 형식 `[A-Za-z0-9._-]{1,64}` 가정. 교체 시 구 kid 공개키 유지는 Rust(041) 측.
- env.ts: `LICENSE_SIGNING_PRIVATE_KEY`·`LICENSE_SIGNING_KID`는 이미 있음(읽기만). 프록시 신뢰 범위 변수는 없음 → 요청 줄(`apps/web/src/lib/env/schema.ts` serverEnvSchema 안): `TRUSTED_PROXY_HOPS: z.coerce.number().int().min(0).max(5).default(0),` (지금은 `deps.ts`가 `VERCEL=1`이면 1홉, 아니면 0홉).
- `device_label`: zod로 받지만 `activate_license`·`activate_plan_device`에 인자가 없어 저장하지 않는다(스키마/RPC 변경 필요, 001 소유).
- 플랜 기기 한도: DB `activate_plan_device`는 조직 단위 `max_activations`(체험 1)인데 04_API·PRD는 "조직별 사용자당 2대, 체험 1대"(D-H5 ③). 시리얼 라이선스도 DB는 라이선스당 `max_activations`. 사용자당 한도·`seat_id` 기록은 DB 변경 필요(074a).
- `activate_license`는 `p_user`가 라이선스 조직 멤버면 세션 조직과 달라도 활성화한다(개인↔팀 교차 금지는 ADR-001 4.7). 파일 `org_id`는 라이선스 조직. 세션 조직 일치 강제가 필요하면 RPC에 `p_org` 추가(DB 변경).
- `last_eligible_build`: `arch.eligible_build`가 service_role 전용·042 소유 → list에서 null.
- 레이트리밋 저장소: 메모리 기본(인스턴스별). 운영 전 `core.rate_limit_hit` 또는 Redis 구현 필요.
- refresh가 `last_seen_at`·`release_confirmed_at`을 갱신하지 않음(전용 RPC 없음, 05장 2.7 좌석 냉각 조기 종료는 074a).
- 쿠키 세션(W·S 호출자의 list·deactivate): `requireSession`(lib/auth, T-C1) 전이라 Bearer만 받는다.
- CORS(데스크톱 출처 `http://tauri.localhost`): 이 라우트에 붙이지 않음(T-C2, Rust HTTP 호출이면 불필요).
- `fast-check`가 apps/web 의존성에 없어(package.json 수정 금지) 속성 테스트는 시드 고정 의사 난수 반복(정준화 300회, clamp 500회)으로 대체.
